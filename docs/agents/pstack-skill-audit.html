The first ten

Importance is a fit score, not a quality score. It combines observed repetition, likely error reduction, alignment with your stack, and the cost of collision with skills you already use.

01

prove-it-works

essential

This should be the default finishing gate. It demands evidence from the real artifact instead of accepting a build, a proxy check, or an agent's claim.

Evidence: tests and verification appeared in 1,408 sessions. The repo also defines explicit verification commands for Nix, shell, formatting, and Docker.

10.0importance
02

type-system-discipline

essential

One portable rule set covers Rust enums, Dart sealed models, TypeScript unions, and parsed Nix or CLI boundaries. It also reinforces your explicit ban on TypeScript any.

Evidence: 470 Flutter/Dart, 398 Rust, and 311 TypeScript/web session matches. The categories overlap, but typed code is present across every major project family.

9.8importance
03

fix-root-causes

essential

Your history is full of fixes, migrations, state bugs, and post-merge audits. This skill is short, concrete, and good at stopping agents from adding guards that hide the actual failure.

Evidence: debugging and fixes appeared in 1,127 sessions. Nix, caches, generated files, and agent state make its restart-state guidance unusually relevant.

9.7importance
04

blast-radius

essential

This is the best match for your release rhythm. It looks past the diff, identifies the fact a change depends on, then proves that fact by running real code.

Evidence: git, PR, and CI work appeared in 1,368 sessions. Your main projects are libraries, CLIs, plugins, and shared infrastructure where a local diff can have a wide downstream effect.

9.5importance
05

how

high

Use this before non-trivial edits in unfamiliar or long-lived subsystems. Its value is the runtime trace and ownership map, not another file summary.

Evidence: architecture and refactor language appeared in 413 sessions. The corpus also spans large repositories such as monochange, solana_kit, openbudget, oh-pi, and pina.

9.2importance
06

laziness-protocol

high

This is your "simple wins" preference translated into code review behavior. It pushes deletion, flat call paths, one source of truth, and the smallest useful diff.

Evidence: the repository's global instructions explicitly ask agents to challenge over-engineering. Refactor and architecture work is common enough for this to pay off without becoming ceremony.

9.0importance
07

recall

high

This addresses a real tax in your workflow. It reconstructs current state from chat history, the working tree, and the shared record before another agent starts changing code.

Evidence: resume and context-recovery language appeared in 335 sessions. The same projects recur across multiple harnesses and worktrees, which raises the cost of a bad handoff.

8.8importance
08

boundary-discipline

high

Validate external input once, keep transport types out of the domain, and put logic in pure functions. That is a strong common rule for CLIs, config loaders, Solana RPC, Flutter services, and plugin adapters.

Evidence: CLI and tooling appeared in 674 sessions, Nix and dotfiles in 637, and Solana or blockchain work in 318.

8.6importance
09

technical-writing

high

Use it for public documentation, RFCs, and longer release notes. Do not trigger the full standard for every chat reply or tiny commit message. It is useful because it is specific, and annoying when applied indiscriminately.

Evidence: documentation and explanation language appeared in 1,125 sessions. PR-heavy delivery also means prose regularly becomes part of the artifact.

8.3importance
10

unslop

high

The useful part is not its blacklist of AI words. It is the demand for concrete claims, shorter sentences, active voice, and a self-audit before prose ships.

Evidence: your global instructions care about voice and concise communication. This skill also improves the output of technical-writing, blast-radius, and PR workflows.

The next ten

These are installed as opt-in tools. Each one has a narrow trigger and a higher process cost than the first ten.

11 / 7.9

architect

Sketching types and module boundaries before implementation would help on large Rust, Dart, and TypeScript changes where the wrong shape is expensive to unwind.

Use for new subsystems and structural rewrites.
12 / 7.8

model-the-domain

This complements type-system-discipline when state machines, registries, or command models can replace scattered booleans and repeated branches.

Use when a second boolean or repeated branch appears.
13 / 7.7

minimize-reader-load

It gives your simplicity preference a measurable review test: fewer layers to trace and less mutable state to remember.

Use during refactors and maintainability reviews.
14 / 7.6

sequence-verifiable-units

Your migrations and multi-package releases benefit when every step ends in a state that can be checked before the next change starts.

Use for migrations, release stacks, and broad sweeps.
15 / 7.5

subtract-before-you-add

This is a useful pre-flight for redesigns. Removing stale adapters and duplicate checks first keeps new work from growing around dead structure.

Use before additions that touch old architecture.
16 / 7.4

interrogate

Independent model reviews can expose blind spots in risky changes. It is too costly for ordinary diffs, but useful before a consequential merge.

Use for security, persistence, and public API changes.
17 / 7.2

why

It traces rationale through commits, issues, docs, and operational data. That is valuable when changing old constraints, but excessive for routine code reading.

Use before reversing an established design decision.
18 / 7.1

create-verification-skill

A project-specific control skill can prove Flutter screens, CLIs, and services through their real user path instead of relying on generic test commands.

Use once per important app that lacks a live control path.
19 / 6.9

show-me-your-work

A compact decision log helps when an agent works unattended for hours. It would be noise during the short, interactive tasks that make up most of the corpus.

Use for overnight and multi-phase autonomous work.
20 / 6.8

make-operations-idempotent

Rebuilds, migrations, release commands, and agent automations all face partial failure. Convergent reruns reduce cleanup and recovery work.

Use for commands that may restart or retry.

Method

The ranking is reproducible enough to challenge. It is not pretending that keyword counts can explain intent on their own.

Scoring weights

  1. Observed repetition, 40 percent.
  2. Likely defect or rework reduction, 25 percent.
  3. Stack and project fit, 20 percent.
  4. Cross-harness portability, 10 percent.
  5. Low overlap with existing skills, 5 percent.

Limits

  • Session categories come from keyword heuristics, not manual labeling.
  • Generated or injected context may raise some counts.
  • Categories overlap.
  • Claude Code transcripts were not present on disk.
  • Scores express personal fit, not objective skill quality.
